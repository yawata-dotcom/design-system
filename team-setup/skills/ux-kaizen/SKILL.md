# ux-kaizen｜社内システムの画面を使いやすくする手順

社内システム（Esupport総合管理システムの各製品）の画面を、全社ルールの中で使いやすくするための手順です。
AI が「調べる・案を出す・絵にする」を受け持ち、**決めるのは社長**です。

> このファイルは公開リポにあります。ここにも、作業で作る物にも、実在の人の名前・実データ・鍵を書かないこと（RULEBOOK §10）。

## いつ使うか
- 使う：「使いにくい」「見づらい」「他と違う」「迷う」「押す場所が分からない」「画面を見直して」
- 使わない：計算・保存・権限など中身の不具合（それは各製品のバグ取りの手順で）

## 守ること（社長がすでに決めた物。ここで新しい決まりは作らない）
1. **全社ルールが先**：RULEBOOK・見本帳・公式17色・Material のアイコンだけ。外から入れた汎用の UI スキル（ui-ux-pro-max など）の配色・スタイル・フォントの提案は使わない。汎用スキルから借りてよいのは「点検の観点」だけ。
2. **今ある型でそろえる案を第一に**：その製品で既に使っている型（行を押す→右の引き出し、下線のタブ、見出し→絞り込み→一覧→詳細など）でそろえる案を、必ず最初の候補にする。
3. **新しい部品を作らない**：合う部品が見本帳に無い時は、手を止めて社長に聞く（RULEBOOK §9）。
4. **注意は色だけを第一候補**：入れ忘れ・注意を知らせる時、字・帯・注意書き・確認の窓は足さない。色の意味は RULEBOOK §1 のとおり。
5. **細かい穴に機能を足さない**：社長の操作が増える／直した物が最新にならない時だけ提案する。
6. **決まった事を蒸し返さない**：その製品の決定の記録（台帳・確定書・引き継ぎ書）に「再提案しない」「戻さない」とある案は出さない。

## 手順

### 0. 決まりを読む（毎回）
- RULEBOOK（唯一の正）：`https://raw.githubusercontent.com/yawata-dotcom/design-system/main/RULEBOOK.md`
- 見本帳：`https://yawata-dotcom.github.io/design-system/gallery.html`
- その製品の見本の画面（`mock/`）と、その製品の CLAUDE.md
- その画面について決まっている事（台帳・確定書）。「再提案しない」を書き出しておく

### 1. 描いて並べて採点する
- 対象の画面と、**同じ製品の他の画面**（似た種類の物を2〜3枚）を、見本の画面で実物のまま撮る（playwright のスクショ。画面全体を撮る＝部分の切り抜きにしない）。
- 下の物差しで、画面ごとに ○／△／× と理由1行をつける。物差しは毎回同じ物を使う。

| # | 物差し | 見る所 |
|---|---|---|
| 1 | 部品 | 見本帳の部品だけか。その画面だけの独自の部品はないか |
| 2 | 型 | 同じ製品の他の画面と、操作の型（右の引き出し・下線のタブ・並び順）が同じか |
| 3 | 色の意味 | RULEBOOK §1 の意味どおりか。同じ色が違う意味で使われていないか |
| 4 | 言葉 | 同じ意味に同じ言葉か（「編集」と「修正」を混ぜない）。項目名は元の紙と同じか |
| 5 | 数字 | 一覧の数・金額は右寄せか。¥・カンマの形がそろっているか |
| 6 | 位置と大きさ | タブや表示を切り替えても、列の位置・幅・字の大きさ・行の高さがずれないか |
| 7 | 手数 | よく使う操作が何回押せば済むか。他の画面より多くないか |
| 8 | 入力 | 日付・金額などの入力欄が正しい種類か。必須の印がそろっているか |
| 9 | 重なり | 飛び出すメニューなどが、ヘッダーの後ろに隠れないか（RULEBOOK §11） |
| 10 | 動き | 開け閉めはスライド 0.7 秒か（RULEBOOK §2） |

### 2. 使う人になりきる（仮想ユーザー）
- 次の3つの役になりきって、その画面を使った時の **迷い・不安を「発言」の形で** 出す。どの画面のどこで出た発言かを必ず添える。
  - **毎日使う事務の人**：早く終わらせたい。いつもと違う所でつまずく
  - **初めて使う人**：どこを押せば何が起きるか分からない。言葉の意味で迷う
  - **確かめて決める社長**：一目で状態が分かるか。間違いに気づけるか
- 次に、**独立した批評役を1つ呼ぶ**（Agent の general-purpose）。1 で撮った絵だけを渡し、自分の案は見せずに「この画面は同じ製品の他の画面と何が違うか・どこで迷うか」を言わせる。
- 自分の採点と批評役の結論が重なった所を「直すべき所」とする。重ならない所は、もう一度絵を見て確かめる。
- 仮想ユーザーは AI の想像です。本物の使う人の声の代わりにはならない。社長に出す時もそう書く。

### 3. 今と案の絵を作る（ファイルは直さない）
- 案は、守ること 1〜5 の中で **1つ**。退けた案は「なぜ退けたか」1行を添えるだけ。
- 絵は、見本の画面のファイルを直さずに作る：playwright の `page.addStyleTag({content: '…'})` で CSS を上書きして撮る（中身の並べ替えが要る時は `page.evaluate` で表示だけ変える）。
- 直す前と直した後の数（列の幅・字の大きさ・押す回数など）を、同じスクリプトで測って生の数のまま残す。

### 4. 社長に選んでもらう
- **PNG の図1枚**にまとめて、ファイルとして渡す（画面の中で見せるだけにしない）。図に入れるのは「今」「案」「どこがどう良くなるか」だけ。字は少なく。
- 本文は数行。最後に **2択＋おすすめ1つ＋理由1行**。2択は両方が本当に成り立つ時だけ。片方が成り立たなければ「1案＋理由＋これでよいか」で聞く。
- 1回の返事で聞くのは1つだけ。

### 5. 決まったら直す（見本→本物）
1. 決まった事を、その製品の決まりに従って記録する（台帳・確定書）。
2. その製品の作業の札・PR の決まりに従って、**見本（mock）を先に直し、本物を見本と同じ形で直す**。見本に無い物を本物に足さない。
3. 点検：その製品の `tools/check-*.sh` を全部流し、ルールの番人（design-guard エージェント）にも見せる。
4. 3 と同じスクリプトで「直した後」の数を測り、PR に貼る。直った画面の絵も添える。

## 社長への出し方の型（例）
> **おすすめ：案1（今ある右の引き出しの型にそろえる）**
> - 今：この画面だけ、行を押すと中央に窓が出る（他の画面は右の引き出し）
> - 案1：右の引き出しにそろえる。押す回数は同じで、他の画面と同じ場所に出る
> - 案2：今のまま（窓の形だけ見本帳の形にそろえる）
